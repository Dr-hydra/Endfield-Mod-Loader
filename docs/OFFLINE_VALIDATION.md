# 无实机游戏条件下的开发与验收

当前约束：没有实机游戏验证条件。开发、独立构建、模块包兼容适配、管理界面、平台接入代码和第一人称拆分继续推进，不等待游戏或设备作为开工前提。交付按离线证据验收，游戏内效果单独标明未验证。

## 当前交付目标

完成可独立构建的 EML 管理应用、旧 BE V1 包兼容层、离线模块宿主、双端接入代码与第一人称示例。管理界面应能用离线宿主导入原包、打开模块网页、保存配置、收发消息和查看日志。游戏启动路径与离线宿主是两个明确入口，界面不能把离线连接显示成游戏已连接。

原 BE 模块包无需修改或重编译；不要求兼容 Next。不做跨产品互斥，保留 EML 自身重复初始化保护。保留已知加载流程并减少迁移时的时序变化，但历史验证不能代表新项目已在游戏中验证。

## 离线验收范围

| 工作 | 可执行的验证 | 不能据此证明的部分 |
| --- | --- | --- |
| 包管理 | 用实际旧 ZIP 验证导入、平台筛选、配置保存、更新、排序、依赖、移除和失败回滚 | 模块的游戏逻辑正确 |
| 原生 ABI | 直接加载已发行 DLL；核对结构、调用约定、导出、返回码、回调与消息 | 每个第三方模块对当前游戏版本适配 |
| 模块生命周期 | 初始化、配置变化、消息、停用/再启用、二进制驻留与升级需重启 | 任意原生模块均能正确收尾 |
| 网页容器 | 实际旧 HTML/JS 和旧 `window.betterEndfield` 接口；验证身份绑定、Promise、回复、事件、状态、页面重开 | 游戏操作已完成；消息接收不等于业务完成 |
| Hook 链 | 自有测试函数上的真实传参、返回、顺序、节点停用和正在执行的回调 | 真实游戏目标的 ABI、地址和功能交互 |
| Windows 启动 | 自有受控测试进程中的标准加载、Host 握手、错误返回和自身重复初始化保护 | 目标游戏的权限、启动时序与实际运行兼容性 |
| Android | Gradle/NDK 构建、JNI 签名/注册核对、JVM 资源发布和解包模拟、ABI/页对齐检查 | 框架在真实游戏进程中的行为、Unity linker namespace 和渲染线程时序 |
| 第一人称 | 专用网格和骨骼数据测试；类型化场景与线程模拟验证切人、退出、资源归属和重试 | 真实画面、角色眼位、遮挡和渲染效果 |
| 打包 | 独立构建、资源完整性、签名核对、安装布局和版本一致性 | 反作弊识别、账号结果或游戏内稳定性 |

Windows 原发行 Echo DLL 已通过研究 Host 验证，记录见 [兼容计划](COMPATIBILITY_PLAN.md)。正式 EML 内部重构后，需要对新的产物执行相同兼容验证，不能直接沿用研究宿主的结果。

## 测试宿主与模拟边界

- 离线宿主真实调用 OS 加载器并执行原 Echo DLL，验证 loader 与旧 ABI。它不假冒游戏。
- Windows 接入使用自有测试进程提供受控生命周期和能力就绪状态，不拿进程创建或 DLL 存在代替 Host 握手。
- 第一人称的模拟对象包含类型、存活状态、所属角色和线程约束，避免使用所有请求都返回成功的桩掩盖恢复错误。
- 旧模块涉及具体游戏接口时，缺失能力返回未就绪或不支持，不能伪造对象或成功结果。Echo 基础装载通过不能代表这一类模块功能已兼容。
- Android 本机原生构建与 JVM 模拟分别记录，不能表述成 APK 已在手机或游戏中运行。

## 开发顺序

1. 正式独立工程、V1 兼容层、离线 Host 和原发行 Echo 回归。
2. 管理界面和旧网页桥，完成“导入旧包 → 连接离线 Host → 打开网页 → 收到回复”的真实闭环。
3. Windows 单一启动接入，在自有测试进程验证加载/握手；Android 完成独立 APK/原生构建和框架适配。
4. 第一人称独立模块，恢复并适配相关生产代码回归，验证资源与线程边界。
5. 整理 SDK、安装包、许可证、文档与验证记录。可交付开发预览版，不以缺少游戏测试无限推迟完成可验证的部分。

## 交付时如何表述

每个产物记录源码版本、构建命令、实际用到的原模块包、通过/失败/未执行结果和限制。发布状态可以是“离线验收通过、游戏内未验证”；不得宣称第一人称已实机可用、所有旧模块功能已兼容或不被反作弊记录。

以后若有外部游戏反馈，将其作为后续缺陷定位证据，不作为当前开发必须等待的条件。
